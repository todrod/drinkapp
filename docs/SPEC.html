The Drink Shaker
Build Spec

Five features on one dark neon surface: a pantry you actually keep current, a generator that only pours what you own, a personal drink book, a spirit browser, and a trending feed that cites its sources or shows nothing at all.

00

Assumptions & open questions

Four things in the brief have more than one reasonable reading. Here is the reading this spec is built on — change any of them and the affected phase changes with it.

Flag 01 — "drink book" is undefined

Assumed: manual recipe entry plus a bundled seed library, stored locally. The user types or edits a recipe, saves it, and can pull a random one back out.

Explicitly out of scope: OCR of a physical cocktail book, and photo-to-recipe import. Both are real products with real cost (camera pipeline, layout parsing, a correction UI) and neither is implied by "stores user-added recipes." Noted as a v2 candidate in Phase 3.

Flag 02 — the reference UI is alcohol-free

The supplied screen reads "Types of non-alcoholic drinks" and its pantry is juice, grenadine, lime, tonic. The written brief says liquor catalog and spirit type. Assumed: one app, one data model, with a Zero-Proof mode switch that filters the catalog and the generator to non-alcoholic ingredients. It costs one boolean on the catalog table and it is the single cheapest way to satisfy both.

Flag 03 — "deep search" for trending

Assumed: a server-side, web-connected retrieval on our own proxy, cached, returning ranked drinks each carrying at least one live URL. Not a crawler, not a scraper of any single bar site, and never a model answering from memory. See Phase 5.

Flag 04 — "party drinking app"

Assumed: a 21+ recipe and hosting tool. No drinking games, timers, dares, or anything that rewards speed or volume. Age gate on first launch, blocking, with the date stored locally. This is a scope decision, not a disclaimer.

01

Stack

The deciding constraint is not rendering — it is that four of five features must work with the router off, and the fifth must not embed a search key in a binary anyone can unzip.

Recommended
Expo (React Native) + TypeScript

Why. One codebase for iOS, Android, and web via react-native-web. Over-the-air updates mean a party-night bug fix ships in minutes without a store review. Expo Go plus a QR code is a genuine distribution channel for this product — you hand the party the app.

With. expo-router (file-based tabs), Reanimated 3 + Moti (the shake, the reveal), expo-haptics, expo-linear-gradient + expo-blur for the glass panels, Zustand for UI state, TanStack Query for the one remote feature.

Runner-up
Flutter

Better at. Pixel-identical output across devices and smoother heavy animation, which this neon-glass direction will lean on.

Costs. Dart, a smaller cocktail/data package ecosystem, weaker web output for a shareable link, and no OTA equivalent. It does not remove the need for a separate backend for trending, so it wins on one axis and ties on the rest.

Live option
Installable PWA

Better at. Distribution. A URL passed around a room beats an install every time, and IndexedDB plus a service worker covers the offline core.

Costs. Weaker haptics and motion feel, no shelf presence, iOS storage eviction risk for a rarely-opened app. Take this if shipping this month matters more than feeling native — Expo web gets you most of it anyway.

Persistence

expo-sqlite + Drizzle ORM. Inventory and recipes are relational and filtered (by category, by spirit type, by "do I own every ingredient"), which is a join, not a key lookup. Key-value stores (AsyncStorage, MMKV) force that logic into JS over a full deserialized blob and get slow at a few hundred rows. Drizzle adds typed queries and versioned migrations, which matters the first time the seed catalog changes shape. MMKV stays for small preferences: age-gate date, units, Zero-Proof mode.

The trending backend

One small serverless function — a Cloudflare Worker, which fits inside its free plan at any realistic scale (see Phase 5) — is required, not optional. It holds the search and model keys, rate-limits, and caches one shared result for all users — so a party of twenty triggers one upstream call, not twenty. Client-side search would put a spendable key in the app bundle. No user accounts, no user data leaves the device; the endpoint takes a region and returns a public list.

Supporting
  • SubstitutionRule — fromId, toId, closeness (0–1), note. Seeded, extendable by the user. The generator only crosses a substitution when closeness clears a threshold and the user has "allow substitutes" on.

  • TrendingDrink (cache only, never merged into the book unless saved) — rank, name, whyTrending, ingredientHints[], sources[], retrievedAt, confidence.
  • TrendingSource — title, publisher, url, publishedAt, snippet. An item with an empty sources array is never rendered.

Matching, in order
  1. Build the owned set. All InventoryItems where level != out, plus every item flagged isStaple.
  2. Filter candidates. Recipes from the seed library and the user's book; apply vibe chips, Zero-Proof mode, and the locked ingredient if set.
  3. Test each candidate. Every non-optional RecipeIngredient must resolve: direct catalogItemId hit, then categoryFallback hit, then — only if substitutes are allowed — a SubstitutionRule above threshold. Track which rule was used.
  4. Score the survivors. Never-made outranks made-before; anything in the last three GeneratorRuns is pushed down; exact matches outrank substituted ones; favorites get a small lift. Pick weighted-random from the top, not strictly best — a deterministic "random" button is the fastest way to make the feature boring.
  5. Render. Substituted lines are marked inline: "Cointreau → using triple sec". Never silently swap.
  6. Zero survivors → FallbackPanel. Never invent a drink and never return a recipe with a missing ingredient.
Fallback copy — the required behavior

One item short: "You're one bottle from 6 drinks. Add lime juice to unlock the Daiquiri, Margarita, and 4 more." — with an Add to Kit button.

Nothing close: "Nothing in your kit makes a full drink yet. Add a base spirit and a mixer, or browse Explore to see what pairs with what." — with Add to Kit and Open Explore.

Filters too tight: "No tropical drinks in your kit — 11 others match. Clear the vibe filter?" The fallback always names the number and offers the single action that fixes it.

05

Trending search

The one networked feature, and the one place the app can lie. The design goal is that fabrication is structurally impossible: no URL, no card.

Verify before building

Search-API terms move fast. Microsoft retired the standalone Bing Search APIs in 2025, and Brave removed its free tier for new signups in February 2026 — new accounts now get about $5/month in credits instead of the old 2,000–5,000 free queries. Re-confirm availability, pricing, and each provider's attribution clauses before committing. Checked 28 Aug 2026. The architecture below is provider-swappable on purpose: one adapter interface, one config value.

Recommended — free, and it cites
Gemini Flash + Google Search grounding

A grounded model call returns synthesized trend findings with citations attached to the claims — ranked drinks, a one-line reason, and URLs, which is exactly this feature's shape. Grounding metadata gives the source list without a second parsing step.

Free allowance: ~5,000 grounded prompts/month on the Gemini 3.x family, plus the Flash / Flash-Lite free request tier. This app needs roughly 240 a month. Same adapter accepts Anthropic's web-search tool or OpenAI's if you'd rather pay for a different voice.

Free backup — retrieval only
Exa, or Serper

Exa refills ~$10 of credits monthly with no card on file, so an overrun is impossible by construction — the safest thing to prototype against. Serper gives 2,500 free queries then roughly $0.30–$1 per 1,000, which at this volume is pennies.

Both return links and snippets and leave ranking to you — so something still has to read the pages and decide what's trending. Use as the retrieval half of a hybrid, or as the failover when grounding quota runs out.

Enrichment, not trends
TheCocktailDB & friends

Useful for canonical ingredients, glassware, and images once a drink name is known. Not a trend source — a static recipe database has no concept of what bars are pouring this month. Use it to fill in the ingredient chips, never to rank.

Free with the public test key for development; a one-off premium key is required to ship publicly on an app store. That fee is the only unavoidable API cost in the whole build, and it buys enrichment, not trends — so it stays optional.

The build: search-with-citations for the ranking and the "why," then enrich each name against the local catalog and a recipe API for ingredient chips. If enrichment fails, the card still renders — name, reason, and sources are the required fields.

Running it on $0

The cache is what makes this free. Because the proxy stores one shared result per region, upstream volume is set by the refresh schedule, not by how many people open the app — four regions refreshed twice a day is 8 upstream calls, about 240 a month, whether you have 10 users or 100,000. What "free" doesn't cover

Store fees are the real cost of shipping native: Apple's developer program is ~$99/year and Google Play is a one-time ~$25. Nothing in the architecture avoids that. Shipping the Expo web build as an installable PWA does — static hosting is free on Cloudflare Pages, and it is the genuinely $0 path to putting this in someone's hand at a party.

The self-hosted floor: a SearXNG instance removes every third party, but you are then running and maintaining a search server, and result quality and uptime become your problem. Only worth it if avoiding vendors is itself the goal.

Query strategy

Fan out across several phrasings rather than trusting one query, then merge. Year and quarter are injected at runtime, never hardcoded — a stale year is the most common way this kind of feature silently rots.

Q1  "top trending cocktails global bars {year}"
Q2  "cocktail trends {quarter} {year} bartenders"
Q3  "World's 50 Best Bars {year} signature cocktails"
Q4  "most ordered cocktails {region} bars {year}"
Q5  "{year} drink trends" site-biased toward bar & drinks trade press
Q6  zero-proof variant: "non-alcoholic cocktail trends {year}"

merge → normalize names (case, "the", punctuation, known aliases)
      → cluster near-duplicates ("Spicy Marg" = "Spicy Margarita")
      → drop anything published > 12 months ago
      → drop anything with zero resolvable URLs
Ranking
  • Independent-source count is the dominant term — a drink named by four unrelated publishers outranks one with a single enthusiastic write-up.
  • Recency decay over the last 12 months.
  • Publisher weight: drinks trade press and bar-industry awards above general lifestyle aggregators, which are frequently recycling each other.
  • Confidence label: 3+ independent sources = normal card. 1–2 = the card renders with a "single source" tag rather than being hidden, so the user judges it.
  • No bar recommendations unless a source names the bar. The feature surfaces drinks; venue claims require an explicit citation on that specific claim or they are dropped upstream.

06

Suggested build order

Each milestone is independently demoable, and the offline core is complete before any network work starts.

  1. Shell + age gate + seeded catalog. Tabs, tokens, SQLite migrations, the bundled catalog landing in the DB. Nothing to show but everything downstream depends on it.
  2. My Kit CRUD. First real demo: add, level, delete, undo, starter kit.
  3. Shaker. The matching algorithm and all three fallback states. Ship the fallbacks in the same milestone — they are the feature, not an edge case.
  4. Drink Book. Editor, grid, Surprise Me, catalog-resolving autocomplete.
  5. Explore. Mostly read-only over data that already exists by now.
  6. Trending. Proxy first with a hardcoded fixture, then the live adapter, then the cache and degraded states.
  7. Polish. Motion, haptics, reduced-motion path, Dynamic Type audit, contrast pass.
Still open

Multi-device sync (currently local-only by design — adding accounts changes the privacy story and the backend). Sharing a kit between guests at the same party. Shopping-list export from the "one bottle away" fallback. Whether the seed recipe library ships bundled or downloads on first run.
